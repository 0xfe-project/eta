# GitHub

Agents use GitHub as **a single GitHub App**: users create and install it via the wizard in “Settings → Connections” and can authorize it to act on their behalf. After authorization, all agents act in the user's name (shown as the user on GitHub, with the App's badge); without authorization, they act as the App's bot identity. There are no per-agent credentials.

This is the forge service from the main-branch AXP (`apps/control-plane/internal/{github,forge}`) ported into the single-process host machine: rules, prompts, tool names, and skill text are all reused; only the pipeline changed—Go control plane + Postgres + REST + files on a volume became a TypeScript plugin + SQLite + wire target in the host machine. The code is in `apps/eta/src/github/`.

## Toggle: not loaded by default

This chain is **opt-in** and off by default: `--github`, or the env var `ETA_GITHUB=1` (`--no-github` overrides the env var). Like the `--memory-url` group, the switch is in `apps/eta/src/main.ts`, then down to `startHost({ github })` / `createProduct({ github })`; tests likewise pass it directly (`github: true`, or `{ endpoints }` pointing at a fake GitHub).

When off, none of it is built: no `new Github`, no `GitHubKeeper`, no `mount("github")`, no `githubSessionTools` registration (the agent's tool list has no `open_pull_request` or `draft_issue`), no callback routes registered (`/github/manifest/callback` and `/github/authorization/callback` are answered by nobody), no `githubRefresh` dispatched, no GitHub credentials in the session shell's environment, and the host's own `eta:github` akhook layer is not registered either. It is not counted in the set of plugins to wait for, so startup does not waste a `MOUNT_TIMEOUT_MS` wait. **Not a single GitHub API request is sent** (not “sent but failed”).

The UI hides based on whether `hello.mounted` contains `github` (`useGitHubMounted`), without asking configuration again: settings has no 「Connections」, task details have no delivery row, tool activity in old timelines that references a PR / issue draft draws no card (only the tool call itself remains), and it does not subscribe to `github`. Old rows are always left undrawn rather than drawn as an empty box: a card that points to another system and whose source is not on this host would make people think the feature is still there.

This is **hiding, not deleting**: the tables, rows, migrations, copy, and code all remain; with the flag turned back on, behavior matches today.

## Who acts as whom

| Scenario                          | Identity                                                                                                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `git`, `gh` (the session's shell) | The user has authorized the App: the user's user-to-server token (`gh auth status` is the user); otherwise the App's installation token (bot)                                   |
| commit author                     | Always the App's bot (`<slug>[bot]`, email `<bot id>+<slug>[bot]@users.noreply.github.com`)                                                                                     |
| `open_pull_request`               | Try the user's token first; if GitHub rejects it (401 also forgets the authorization; 403 and 404 mean the user lacks permission), silently open it as the App instead          |
| Read PR, merge PR (task page)     | The user's token; if there is no authorization or it is rejected (401), the App. If GitHub rejects the merge, that is the answer; it will not switch to the App and merge again |

The App is public (users can install it on their other accounts and organizations), `request_oauth_on_install`: during installation GitHub also asks the user to authorize, so most users are already “acting as the user” once installation finishes. The token's permissions are exactly what the user granted at install time; when creating the App, the manifest requests the highest level available for repositories and organizations from GitHub.

## Create and install (wizard)

Settings → Connections → GitHub, four steps: Learn → Create App → Install to repositories → Done. The wizard reads the `state` of the `github` target; the current step is determined by the host's state.

1. **Create**: `github.createApp { name, organization?, origin }` validates the name (≤ 34 characters, letters, numbers, spaces, `._-`) and organization name, and returns `{ action, manifest }`. The browser POSTs the manifest to GitHub as a form (GitHub only accepts this method); `action` carries a one-time `state` generated by the host (`github_pending`, valid for 1 hour). The manifest's `redirect_url` is `<origin>/github/manifest/callback`, `callback_urls` is `<origin>/github/authorization/callback`, and the webhook URL is written but `active: false` (nothing listens for webhooks, so there are no webhook routes).
2. **Return**: GitHub sends the browser back to `GET /github/manifest/callback?code&state`. The host consumes `state`, exchanges `code` with GitHub for the App's credentials (id, slug, private key PEM, client id/secret), stores them in the database, and 303s to `/?settings=connections&github=created`; on failure, `…&github_error=<reason>`, and the page reopens the wizard and shows the reason. When an App already exists, it cannot be created again (`GITHUB_ALREADY_CONNECTED`).
3. **Install**: The user installs the App on GitHub. While waiting for the first installation, the page has the host re-ask GitHub every 5 seconds (`github.refresh`), and also asks once when the window regains focus. `state` is `not_connected` / `not_installed` / `ready` / `error`; `error` carries GitHub's reason, and GitHub no longer recognizing this App (401) is `GITHUB_APP_GONE`, prompting the user to disconnect and reconnect.
4. **Authorize** (optional; also what GitHub asks incidentally when installation completes): see below.
5. **Disconnect**: `github.disconnect` deletes the App's credentials and the user's authorization (the App on GitHub is not deleted; the prompt includes a link to delete it).

The redirect URL's origin comes from `--public-url` (or `ETA_PUBLIC_URL`); if absent, it uses the `location.origin` reported by the page, consistent with [MCP's OAuth callback](mcp.md#oauth).

## User authorization

`github.authorize { origin }` returns GitHub's authorization URL (PKCE: `code_challenge` S256; `state` and verifier are recorded in `github_pending`, valid for 15 minutes). The callback `GET /github/authorization/callback` arrives in three ways:

- With `code` and a `state` issued by the host (clicking “Go to GitHub authorization” in the wizard);
- With `code` and `setup_action`, and **no** `state` (the authorization GitHub incidentally requests during App installation; GitHub does not return state);
- Only `setup_action` (installation complete, no authorization requested): only tells the page “installed” via the URL.

After exchanging for a token, always verify: this GitHub account **can access one of this App's installations** (`GET /user/installations`); otherwise do not save it (`AUTHORIZATION_UNRELATED`), to avoid connecting someone else's account. For the arrival without `state`, the host cannot match it to one of its own clicks, so there is one extra rule: a personal App only accepts the App owner's own account (organization Apps do not add this rule); otherwise have the user return to settings and authorize via the wizard. (The main branch does not have this rule; this is a tightening added during the port.)

The token lasts 8 hours and the refresh token 6 months; each refresh renews both, and **a refresh token can only be used once**, so refreshes are serialized (`Github.#locked`). If GitHub rejects a refresh, forget the authorization. Unauthorizing (`github.unauthorize`) first revokes on GitHub (`DELETE /applications/{client_id}/grant`, best effort) and then deletes. Apps that predate the host storing a client secret have no secret: in the wizard, have the user enter the Client ID and a newly generated secret (`github.setOAuthClient`).

The token the host gives the machine lasts **at most one hour** (`credentials()`), so after unauthorizing in eta, it switches back to the bot within an hour.

## Where it is stored

Migration 0035:

| Table            | Content                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `github_app`     | Single row. App public info in plaintext; **private key, client secret sealed** (`apps/eta/src/secret.ts`, AES-256-GCM, `secret.key`)      |
| `github_user`    | Single row. Login name, id in plaintext; **access token and refresh token sealed**                                                         |
| `github_pending` | In-progress creation (manifest) and authorization: one-time `state`, PKCE verifier, redirect address. Deleted once used, cleared on expiry |
| `task_pull`      | PRs delivered by a task: `task_id` (foreign key, cascades when the task is deleted), `url`, `title`, `number`, `opened_at`                 |

A sealed row that cannot be read (key changed or tampered with) counts as absent: the App reads as not connected, the user reads as not authorized. Keys, secrets, and tokens never go on the wire: the wizard gets the address to open and the manifest to POST.

## Tokens and calls

The `Github` class (`service.ts`). Calls as the App use a JWT (RS256, `iss` is the App id, valid for 9 minutes); calls as an installation use an installation token (cached until less than 10 minutes from expiry). Installations are found by owner (use the 30-second cache first, ask GitHub once if not found); `credentials()` uses the installation on the **App owner's** account. A missing installation is `GITHUB_NOT_INSTALLED`, and the message tells the user to install from "Settings → Connections".

GitHub failures are always 424 (not 502 — Cloudflare replaces origin 502/504 with its own error page); the `GithubError` object carries `code`, `message`, `status`, and the message is the original Chinese text, shown directly by pages and tools.

## Tools

`open_pull_request`, `draft_issue`, with names, parameters, and descriptions following the main branch's forge MCP server. Built as **session tools** (`githubSessionTools`, wired into `combineSessionHooks`) instead of standing up an MCP server:

- The tools run in the host process, and the host already holds each session's tool list; there is no need for an MCP client, port, and credentials to reach something in the same process.
- Sessions on a daemon have these two tools as well: product tools go back to the main node via `tool.call` to execute, so the App's keys never leave the main node.
- The tool result's `details` says what it produced (`pull_request` or `issue_draft`), and the page draws a card under the tool row from it (`activity-ref`); the `draft_issue` card opens GitHub's prefilled new-issue page, and when the body is too long to fit in the link the card carries "Copy body".

If `open_pull_request` finds an already-open PR for the same head, it returns it (`created: false`). `draft_issue` never touches GitHub and works without a connection; when the link exceeds 8000 characters only the title is filled in, and the body is carried to the page with the result (which is why the daemon's `details` limit for tool activity is raised to 70,000 characters).

## Tasks and PRs

The board knows nothing about GitHub. After `open_pull_request` succeeds in a session, the host records a row in `task_pull`: the task is the most recently touched one this conversation is **still working on** (todo / in_progress / in_review / blocked). If there is none, nothing is recorded. The `github` target's `pulls` is this table; the task page's "Deliveries" row (`TaskPulls`, attached to the children of `TaskProperties`) lists them, each showing its current state on GitHub, line counts, and allowing a merge:

- `github.pull { url }`: read the PR live (`open` / `draft` / `merged` / `closed`, +/− line counts, `headSha`, whether it can merge `ready` / `pending` / `blocked` and why). The PR link must be a github.com `…/pull/<n>`.
- `github.merge { url, headSha }`: merges only the commit the page saw (a mismatched `sha` is `STALE_HEAD`), using the first merge method the repository allows (squash, merge, rebase); **never** bypasses protections: no admin override, no auto-merge, no branch deletion. A lost answer (network, timeout, GitHub 5xx) is not retried: read once more — merged at `headSha` counts as success, otherwise `MERGE_UNKNOWN`. Only one merge per PR can be in flight at a time.
- "Merge and mark the task complete" is two steps: the task is set to complete only after GitHub merges successfully, and a failed completion can be retried on its own without merging again.

## git and gh on the machine

`GitHubKeeper` (`apps/daemon/src/github.ts`, shared by host and daemon) writes the token under each machine's `<data directory>/github/`, refreshes it on a routine (5 minutes before expiry, retrying 1 minute after a failure), and maintains a shared environment object `env` that the session shell reads on every command:

- `GH_CONFIG_DIR=<dir>/gh`: `gh/hosts.yml` is gh's login to github.com (the username is the authorizing user or the bot);
- `GIT_CONFIG_COUNT/KEY/VALUE`: `credential.https://github.com.helper` (first clear the machine's existing helpers, then a shell function that reads the `token` and `login` files) and `include.path` (`git/github.inc`, so the commit author is the App's bot).

With no GitHub connection, `env` is empty and there are no files in `github/`, and the machine's own gh/git login stays as it was; connecting, authorizing, and disconnecting take effect immediately for already-open sessions (the environment object is read once per command), no reopening needed. The `token` file is written last, after the other files, so its presence means the rest are there.

- Main node: taken directly in-process (`Github.credentials()`).
- Daemon: asks the main node over the link; `svc` calls `github.credentials`, returning `{ token, expiresAt, identity, user? }` or `null` (not connected). When the main node connects, authorizes, or disconnects it sends `machine.githubRefresh` to online daemons so they re-ask right away instead of waiting for the next refresh. If the link is down, the login on disk is left untouched. **The daemon holds no App private key, client secret, or refresh token**, only a token valid for at most an hour.

## akhook

The host layer `eta:github` (`github/akhook.ts`) carries the `gh-pr-create` rule: if `shell_exec` hits `gh pr create` it is blocked, with the message "Push the branch, then open the PR with the open_pull_request tool.". It is a host layer, so user and project akhook files can neither disable nor override it, and it ships to daemon sessions along with the other host layers. The rule guards against mistakes, not an agent deliberately working around it: what is truly disallowed is enforced by credentials.

(Another main-branch `akhook-approval` manages Codex's one-time authorization file; here ask rules go through the inbox, with no counterpart, so it is not ported.)

## wire：`github` target

Two sections: `state` (`GitHubStatus`: `state`, `app`, `installations`, `error`, `user`, `oauth`, `checked`) and `pulls` (`TaskPullView[]`). `checked` false means the host has not asked GitHub yet since starting, and the page shows loading.

| Action           | Description                                                                       |
| ---------------- | --------------------------------------------------------------------------------- |
| `refresh`        | `{ fresh? }`: asks which accounts GitHub is installed on, returns the new `state` |
| `createApp`      | `{ name, organization?, origin }` → `{ action, manifest }`                        |
| `setOAuthClient` | `{ clientId, clientSecret }`                                                      |
| `authorize`      | `{ origin }` → `{ url }`                                                          |
| `unauthorize`    | Revoke the user's authorization                                                   |
| `disconnect`     | Forget the App and authorization                                                  |
| `pull`           | `{ url }` → `GitHubPull`                                                          |
| `merge`          | `{ url, headSha }` → `GitHubPull`                                                 |

## Access control

The two callbacks are **exact, read-only paths** exempt from the token gate (see [Access control](access.md)): `/github/manifest/callback` and `/github/authorization/callback`; a browser returning from github.com does not carry our cookie. The credential is the `state` issued by the host: missing, wrong, already used, or expired — nothing changes; it just redirects to the settings page with a reason. They do nothing else.

## UI

Settings → Connections (`connection-settings.tsx`): one GitHub row, with “Start connecting” or “Manage” on the right, a status badge, and one sentence (as whom, pending installation, error). The wizard (`github-wizard.tsx`) is a dialog with a step bar. GitHub's callback brings `?settings=connections&github=created|authorized|…` back to the home page; the settings dialog opens accordingly; when the wizard reads `github`, `github_error`, or `setup_action`, it shows a notice and reopens at the current step, then removes these parameters from the address. When the host has no `github` plugin, this settings item is hidden.
