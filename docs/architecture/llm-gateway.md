# LLM gateway

The LLM gateway lets the main node generate directly with model **subscriptions** (ChatGPT Codex, Grok) and **Google AI Studio API keys**, and shows account status and subscription quota. It and the upstream API key providers are two sources in the same model layer: providers come from `config.json`, while the gateway's models come from the accounts it is connected to.

## Components

```text
Bun process (host)  apps/eta/src/llm/                         child process
  runtime.ts   startup, wire up the model layer ─────────────── HTTP 127.0.0.1:N /v1 ─────────▶  CLIProxyAPI v8.0.43
  cpa.ts       starts and supervises CPA via @cpajs/cpa ─── HTTP 127.0.0.1:N /v8/management ▶  (@cpajs/<platform> binaries)
  gateway.ts   accounts, directory, quota, login
  state.ts     derives state from CPA's cooldown view
  codex.ts xai.ts gemini.ts   connectors
  models.ts    GatewayModels (llm provider)
  plugin.ts    llm target（accounts models quota）
```

- **Child process**: CPA is an official binary, installed per platform by [`@cpajs/cpa`](https://github.com/akarachen/cpajs) (`0.1.0-rc.7`, bundling CLIProxyAPI **v8.0.43**) via `optionalDependencies`; `bun install` is enough, and Go is not needed. `startServer` writes config, picks a free port, and waits for `/healthz`; CPA is started via cpajs's launcher, with `PR_SET_PDEATHSIG` on Linux and supervision by the launcher on other POSIX systems, and **CPA also exits when the host is SIGKILLed or crashes**.
- **Self-healing**: when CPA exits on its own (crash, killed), `cpa.ts` waits a bit, then starts another one with `startServer` (cpajs only starts and stops; it does not restart automatically). The new process gets any free port: `cpa.client` and `cpa.baseUrl` are switched to those of the new process, and after `runtime.ts` receives `onRestarted`, it re-registers the `llm` provider at the new address (it does not try to grab the original port: re-registering regardless of whether the port changed is simpler than “try the original port first”). The wait starts at 0.25 s; if the process dies again within a minute, it doubles (up to 30 s); if it stays alive for over a minute, it returns to the minimum. There is no cap on attempts, and it never gives up. On exit, CPA's last 20 lines of output are written into the warning. First startup failure is not retried: the host starts as usual, with no gateway, and shows a one-line notice.
- **Fails to start**: if CPA fails to start, the host starts as usual and shows a one-line notice; there is no `llm` plugin, the web UI has no “Subscriptions and keys” section, and everything else is unchanged. With `--no-llm`, it is not started.

### Boundary with CPA

Only CPA's HTTP interfaces are used: `/v1` (model traffic) and the v8 management API (`/v8/management`, via cpajs's typed client); its internal packages or SDK are not relied on.

- **Config**: `<state directory>/config.yaml` is rewritten by the `config` function before every start: the host's settings (loopback, the `/v1` key, control panel and request logging disabled, `request-retry: 1`) plus the `api-keys` left in the config from the previous run (this is the section changed at runtime through the management API), with tests additionally merging in `cpaExtra`. So the single source of truth for API keys is CPA's config. When changing a key (`updateKeys` in `connectors.ts`), it reads the `api-keys/<provider>` node and its ETag, strips the `auth_index` injected on read, writes back with `If-Match`, and on 412 re-reads and re-modifies (up to 3 times); no in-process lock is added; concurrency relies on the ETag. CPA does not write config atomically; a read that lands in the middle of a rewrite gets a 500 `invalid_config`: this is not retried here; the sync every 5 seconds will handle it next round, while a user operation reports `gateway_unavailable` once.
- **Authentication**: CPA's `/v1` accepts only one key, randomly generated on every start and never leaving the host process; the host's own model layer uses it directly to call CPA.
- **Management API**: the management secret is randomly generated by cpajs on every start; only its bcrypt hash (cost 4) goes into the config, while the plaintext stays in `server.client()` and never passes through the host; remote management is disabled. CPA verifies the hash on every management request, about 1 ms at cost 4 (about 65 ms of CPU at cost 10, while the gateway needs to read several times every few seconds).
- **Logs**: CPA logs every request at info; only warn and above (filtered by the `LogLine.level` parsed by cpajs) and lines on stderr without a level (such as panics) are forwarded to the host's stderr (prefix `[cpa]`); the startup banner on stdout without a level is not forwarded. The full recent output is in cpajs's `recentLogs`, and is attached to the warning when CPA exits unexpectedly.

## Accounts and directory

Connectors only handle “how credentials get in”; listing, enabling/disabling, and deleting accounts are all handled in `gateway.ts`: the list is `GET /credentials` (credential files) plus `GET /config/api-keys` (keys in the config, with `auth_index`; a key or group is disabled if its `excluded-models` contains `*`). Credential files go through `PATCH /credentials/status` and `DELETE /credentials` by filename; keys in the config are changed by eta via `api-keys.<provider>` (disabling adds `excluded-models: ["*"]`, the same as CPA itself does; deleting removes it from the group, and if the group becomes empty, removes that too). An account id is CPA's `auth_index` (derived from the credential, unchanged across restarts).

- **Codex**: OpenAI's device-code flow (`/api/accounts/deviceauth/usercode` → poll `/deviceauth/token` → `/oauth/token`), without relying on a localhost callback. In CPA's management API, Codex only has the localhost-callback flow, so the device-code protocol is implemented in `codex.ts`, and the resulting token is given to CPA via `POST /credentials` in CPA's codex credential-file format.
- **Grok (xAI)**: calls the management API's `oauth/auth-url` (`provider: xai`, device code) / `oauth/status` / `oauth/session`; CPA stores the credentials itself.
- **Google AI Studio**: enter an API key. On submit, validate it against Google first with `GET /v1beta/models`; a duplicate key is an error; the key is written to CPA config's `api-keys.gemini` and takes effect live. An invalid key is judged `needs_login` (reason code `invalid_api_key`). A `providers.json` left by the Go gateway is merged into the config on first start (disabled ones stay disabled), then deleted.

Upstream eta's built-in Codex login (the `providers` plugin, pi-ai's OAuth) is still there, and the two are independent: that one is the upstream provider `openai-codex`, this one is a subscription account via CPA, with model ids starting with `llm:`.

### Status

State follows how CPA actually routes and is derived on read (`state.ts`); the gateway stores no state of its own and runs no routines: `active`, `disabled`, `needs_login`, `rate_limited`, `error`, `degraded`, with a reason code (see below) and recovery time, no token.

- A credential file's status comes from `GET /credentials`: `status`, `status_message` and the **cooldown view** (`cooldowns`: applying to the whole credential or to a single model, with reason `credential_quota`/`quota`/`unauthorized`/`invalid_grant`/`payment_required`/`not_found`/`transient_error`… and recovery time, computed by CPA's `CooldownSnapshotForAuth` according to its own routing rules).
- CPA records a request failure on the model, after which only that model is cooled down and other models still route to this account as usual. So only failures of the credential itself affect the whole account: any cooldown whose reason is `unauthorized`/`invalid_grant`, or `status: error` with a message that looks like login expiry (`needs_login`); credential-level cooldowns (`credential_quota` → `rate_limited`/`quota_exhausted`, `quota` → `rate_limited`, `payment_required` → `error`, everything else → `degraded`).
- **API keys have no runtime state**: CPA's v8 management API doesn't list the keys in the config (`/credentials` lists only credential files), so their cooldowns aren't visible either. A key's state is just enabled or disabled, plus the gateway's own checks (see “Quota”): when Google rejects a key it is judged `needs_login`. A key's 429 or model cooldown isn't shown in the UI, and CPA routes according to the cooldown anyway.
- Transient failures (timeouts, 5xx) are cooled down by CPA for about 1 minute, and during that time the next request for the same account and same model is rejected too; it recovers when the cooldown expires.
- A model's status is `available`, `degraded` (cooling down, requests still pass), `unavailable` (unbound, disabled, login expired, no permission, not found, quota exhausted, with a reason). When several accounts serve the same model, the best one wins. Models seen are persisted in `models.json`; after an account fails or is removed the model stays in the catalog, agents keep their original choice, and it recovers automatically once rebound. Non-conversation models such as image and video are filtered out.
- Catalog: which models a credential file serves comes from `GET /credentials/models`; a key in the config serves the models it is configured with (by alias, the key's own take precedence over the group's), and with no configuration it is all models of that channel. `excluded-models` only honors `*` (disabled): a disabled key makes its models unavailable through the account state; eta doesn't write other exclusion rules, so it doesn't read them either. Each model's context length, reasoning levels (`reasoning_levels`) and whether it reads images come from `GET /routing/model-definitions/<channel>` (CPA's built-in static definitions, fixed with the binary, read once per channel and cached until the process ends, retried next time on failure), with values given in the config taking precedence; a connector's provider is its channel. Codex's channel definition is the Pro plan table; other plans' models are a subset of it, with details looked up by id.

### Quota

A subscription's quota windows (Codex's 5-hour and weekly, Grok's periodic quota) are read from the provider: Codex reads `chatgpt.com/backend-api/wham/usage`, Grok reads `cli-chat-proxy.grok.com/v1/billing`, via the management API's `POST /requests/api-call` (`auth_index` plus `Authorization: Bearer $TOKEN$`, the token is filled in by CPA and **never leaves CPA**), without consuming quota. One read doubles as the account's health check: when the upstream rejects the token (401), refresh once with `POST /credentials/refresh`, and only if it is still rejected judge `needs_login`; network or upstream failures only record `check_error` on the account and don't change availability. Concurrent `refresh` calls share the same round of checks. API keys have no subscription windows and return an empty window list (for Google AI Studio the check is listing models once).

## The seam with the host

- **`llm` provider**: `GatewayModels` registers the gateway's `/v1` as a provider in the model layer, id `llm`, with model ids `llm:<CPA model id>` (`kind: openai-compatible`, Chat Completions; CPA handles protocol conversion). This provider is rebuilt when the catalog changes; models of other providers are still answered by the model layer built from config. The seam is the `overlayModels` option of `assembleServer`. Don't use `llm` as a provider id in config anymore (the gateway's wins).
- **daemon unchanged**: when a daemon needs to generate it still hands the request to the main node, whose model layer (including `llm`) resolves it and calls the gateway; **subscription credentials live only on the main node**, see [Machines and daemons](machines.md).
- **`llm` target**（`apps/eta/src/llm`，eager）：

| section    | Content                                                              |
| ---------- | -------------------------------------------------------------------- |
| `accounts` | `ready`, connection methods (`connectors`), accounts (`connections`) and their status |
| `models`   | the catalog and each model's current availability and reason          |
| `quota`    | each account's subscription windows (`kind`: `5h`/`weekly`/`monthly`, `used` percentage) |

action: `refresh` (check all accounts and read quota), `loginStart`, `loginPoll`, `loginSubmit` (API key), `loginCancel`, `setEnabled`, `remove`. Accounts and models are read every 5 seconds (a few loopback management requests) and pushed only when something changes; quota is read at startup, after a successful login, on `refresh`, and every 10 minutes. Reasons for failures and unavailability are always **a code plus params**, not sentences: `LLM_CODES` (`packages/client-contracts/src/llm.ts`) is a closed code table, and each code's meaning and params are written in `apps/eta/src/llm/problems.ts`. The gateway returns `{code, message, params}`, where `message` is an English diagnostic only for logs and `params` are `provider` (display name) and `status` (HTTP status). The `llm` plugin passes them through as-is (a failed reply frame carries `problem: {code, params}`; a failure the gateway doesn't explain reports `gateway_unavailable`), untranslated; the web UI translates each code into Chinese and English in `llm:problems.*`, and for an unknown code shows the code and diagnostic. A connection method's login instructions (formerly `hint`) are no longer given by the gateway either; the web UI looks up the copy by connection method id.

- **Usage**: per-call token counts continue to use the `usage` table: the session's `turn:end` carries `provider: "llm"`, the model and tokens, and is accounted per agent; the old gateway's separate “per-principal ledger” (`usage.json`) is no longer kept. Subscription quota windows belong to the `quota` section above.
- **UI**: in Settings → Model services, the “Subscriptions and keys” section lists accounts grouped by connection method (status, plan, quota bars, sign in again, disable/enable, remove); Codex and Grok use a device-code dialog (verification code, authorization link, countdown, polling every 1.5 seconds), Google AI Studio uses a key entry dialog; the “Refresh status” button calls `refresh`. Accounts that need attention make the settings button show a red dot. The gateway's models appear in the model selectors everywhere, grouped by connection method, with unavailable ones greyed out and given a reason. The whole section is hidden when the host has no gateway.

## State directory

`<data directory>/llm/`: `auths/` (CPA's credential files, same format as with the Go gateway, reused as is), `models.json` (models seen, format reused), `config.yaml` (rewritten on every start, whose `api-keys` is the single source of truth for API keys, don't edit by hand).

## Build and test

No build needed: `bun install` installs `@cpajs/cpa` and the CPA binary for the current platform. Upgrading CPA means upgrading the `@cpajs/cpa` version in `apps/eta/package.json` (it pins one CPA version), then running the tests below.

- **State derivation** (`apps/eta/test/llm-state.test.ts`, pure functions): mapping the cooldown view to account state and model state, Codex credential file format and plan names.
- **Gateway against real CPA** (`apps/eta/test/llm-gateway.test.ts`, fake Google and OpenAI logins): Google AI Studio key validation (empty, invalid, duplicate), account and models appearing after writing the config, checks, disable and enable, still there after a restart, models kept as unavailable after removal; the Go gateway's `providers.json` migrating into the config; Codex device-code login becoming a CPA credential file, models coming online, disable and removal; CPA restarting after SIGKILL with a notification, and the `/v1` key and management client working on the new process.
- **Host tests** (`apps/eta/test/llm.test.ts`, real CPA, fake upstream): the `llm` target and models coming online, streaming generation via `host.server.models` and getting tokens, usage recorded with provider `llm`, stopping midway cancels the upstream, an upstream 500/429 fails only that generation.
