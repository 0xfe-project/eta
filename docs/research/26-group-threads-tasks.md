# 26 群（Thread）与「讨论 → 任务」的统一协作流程（设计稿）

AXP 任务 #111。这是一份**待讨论的设计**，不是已定方案：本 PR 只有这份文档，不改业务代码；可交互的原型发布为任务 #111 上的 Artifact，不放进仓库。第 10 节是需要你拍板的问题。

## 0. 摘要

- **今天的事实**：一个智能体 = 一段对话 = 一个 Codex thread。三者在数据库（`message.agent_id`、`agent_session` 一行）、runtime（`Agent` 只有一个 `threadId`）和前端（草稿、附件、outbox 都按智能体）里是绑死的。要有多个群，必须先把「智能体」和「对话上下文」拆开。
- **推荐**：新增一等对象 **群**（内部叫 thread）。群有名字、成员（你 + 1..n 个 AXP 智能体）和简报；它本身就代表「这件事」。**群和任务松绑定**：群可以一个任务都没有，也可以关联多个；任务仍是执行单元，可以从群里起草创建，也可以在别处创建后关联到群，群的侧栏列出它的相关任务；任务的执行（远程 Run、评论、交付物）仍由任务系统管理，群里只显示一张实时更新的卡片，不复制时间线。
- **上下文与记忆**：每个「(智能体, 群)」一条独立的 Codex thread，群的对话上下文不共享；跨群的知识全部走现有的记忆插件，按智能体共享、不按群隔离。群的行为（读群历史、检索、草稿、简报）和记忆都做成**内置、不可关闭的环境包**里的插件（MCP 工具 + skill），不走 CLI，也不写 `MEMORY.md`（§7.3）。
- **多智能体**：只有被点名（或群的默认对象）才被唤醒；智能体的发言默认**不唤醒**别的智能体；看到 ≠ 要执行。唤醒时只给被点名的那条消息，前情由智能体按 skill 用工具自己检索，不做全量投递。首版就支持在一个群里 @ 多个智能体并行回答，交接（智能体 @ 智能体）放第二阶段并带跳数预算。同一智能体跨群串行，在别的群忙时排队（已确认接受）。
- **首版范围**：命名群（最少你 + 1 个智能体）、群列表、成员增删、@ 选择发言对象、多智能体并行回答、从群起草并创建任务、任务卡片回群、旧对话迁移为每个智能体一个"私聊群"。不做多用户/权限/SaaS，不碰 #102 Telegram、#103 Project 的实现。

## 1. 现状审计

代码路径相对 `apps/control-plane/internal`（Go）、`apps/agent-runtime/src`（runtime）、`apps/web/src`（Web）。

| 方面         | 现在是什么                                                                                                                                                             | 对多群的含义                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 对话容器     | `conversation` 表只有一行 `is_default`（`chat.DefaultConversationID`），它其实是**整个工作区**：`agent.conversation_id`、`ui_event`、`agent_event` 的 seq 都挂在它上面 | 不要把它改成"群"——它是事件流的分区。群是新对象，`conversation` 保持"工作区"的含义                    |

| 审批         | `approval` 挂在 `command_id`，`interaction` 挂在 `message_id` 和 conversation；"待处理"跨智能体汇总                                                                    | 通过命令/消息自然带上群；待处理列表要显示"哪个群"                                                    |
| 插话 / 停止  | steer 进入**该智能体正在运行的 turn**；stop 按回复                                                                                                                     | 插话必须限定"同一群的运行中 turn"，否则会把 A 群的话插进 B 群                                        |
| 附件         | `chat_attachment.agent_id`，上传到"当前智能体"；runtime 网关只放行本智能体的附件                                                                                       | 一条消息可能发给多个智能体：附件改为属于群，网关校验"智能体是该群成员"                               |
| Artifact     | `artifact(agent_id 或 computer_id, task_id)`；工具结果 `_meta["axp/ref"]` 投影成活动卡片                                                                               | 卡片天然出现在发布它的那条回复里，即那个群；可选再记 `thread_id` 让群侧栏能列出                      |
| 任务         | `task / task_session / task_run / task_activity`；指派远程智能体后每条评论排一次 Run；AXP 智能体**不是指派对象**；`created_by_agent`                                   | 任务模型不用大改；缺的是"来源群"和"群内卡片"                                                         |
| 任务 ↔ 聊天  | 任务底部「请 Agent 协助」及其对话框由 #238 提供，用于远程执行侧；群用于 AXP 讨论侧                                                                                     | 讨论入口只在任务属性的「群」一行；已关联时打开群，未关联时新建群并关联任务                           |
| 记忆         | mem0 `user_id = agent`（`X-AXP-Agent-Id`），每轮 `prompt_submit` 召回、`stop` 抽取；**没有群/对话维度**                                                                | 默认按智能体共享是对的；但 A 群的事实会被 B 群召回。需要来源标注和"本群不记忆"的开关（见 §7.3）      |
| 工作区文件   | 卷 `/agent/workspace` 是 Codex 的 cwd，按智能体一份                                                                                                                    | 同一智能体在两个群里的工作会碰到同一批文件；首版串行执行可避免同时写，但目录约定要定（见 §7.2）      |

结论：**串话的风险点有四个**——Codex 上下文（必须分 thread）、插话（必须限群）、附件（必须限成员）、记忆召回（默认共享但要可见、可关）。前三个是硬隔离，第四个是产品取舍。

## 2. Raft 参考：核实了什么、借鉴什么、不照搬什么

读了 `botiverse/raft-source` 的 manual 与 `packages/server/src/services`（FSL-1.1，只参考设计，不复制实现）。

- **模型**：channel / DM 存消息；thread 是挂在某条消息下的子讨论，不能独立创建；task 是"顶层消息 + 任务元数据"（编号、状态、认领人），thread 回复不能变成任务（`manual/agent-knowledge/thread.md`、`task.md`）。
- **投递与唤醒**：频道成员**按成员关系**收到每条消息进自己的 inbox（`mention.md`："membership delivers regardless of mention"）；thread 按"关注者"投递；@ 只是"注意力"信号。Agent 是**一个常驻 session 横跨所有频道**，被唤醒后用 `raft message check` 抽干 inbox 再决定回不回（`inbox.md`），唤醒有计划器和崩溃熔断（`agentOrchestrator.wakePlan`、`wakeCrashLoopBreaker`）。
- **源码里核实的几点**（路径相对 `packages/`）：
  - 智能体自己发的消息同样投给频道里的其他智能体，投递时只跳过发送者本人和静音的成员（`server/src/services/messageService.ts`，`if (senderType === "agent" && agent.id === senderId) continue;`）。@ 另外持久化成一条「提及送达」记录，先记后送，丢了可以重投。
  - 投递时在跑的智能体直接进 inbox，没在跑的被启动（`agentOrchestrator.ts` 的 `deliverMessage` → `planWakeAction`）。daemon 在安全断点把一批消息并进下一轮。
  - 一个智能体是**一个横跨所有频道的会话**。系统提示让它在 `MEMORY.md` 里记下「每个频道在聊什么、谁在做什么」，上下文压缩后靠它恢复；回复由智能体自己用 `raft message send --target` 指定发到哪里（`daemon/src/drivers/__snapshots__/systemPrompt/common.md`）。
  - 回不回、会不会插嘴、要不要动手，靠的是系统提示里的规矩：别人在对话时只有被 @ 才加入，只有做事的人汇报，要动手先 `task claim`，系统消息不回。服务端只看了投递这条路径，没找到限制智能体互相唤醒的跳数或预算，这部分靠模型自觉。
- **借鉴**：人和智能体都是参与者；"可见"和"被投递/被唤醒"是两件事；任务有认领、状态、编号；有防崩溃循环的熔断。
- **不照搬**：
  1. Raft 的 thread 是附属物，你要的是**独立命名的主题群**，所以 AXP 的"群"对应 Raft 的 channel，而不是 thread。
  2. Raft 让每个成员 agent 收到所有消息并自行判断——成本高，且一个 session 混着所有频道的上下文。AXP 的智能体是 Codex app-server 驱动的容器，每次唤醒就是一个付费 turn，所以 **AXP 由控制面决定唤醒谁**，智能体不自己轮询 inbox。
  3. Raft 任务 = 消息；AXP 已有独立的任务看板、远程 Run 和时间线，任务不应退化成一条消息。

## 3. 概念

| 概念               | 含义                                                                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 群（thread）       | 一个命名的工作主题。成员 = 你 + 1..n 个 AXP 智能体。有简报，可以归档，没有状态                                                                                             |
| 私聊               | 存储和抽象上就是群：只有你和一个智能体，类型标为私聊，每个智能体**有且只有一个**。想按话题和同一个智能体开多段对话，就建多个只拉它的群——效果上是「无限私聊」，概念上都是群 |
| 发言对象           | 一条消息要唤醒的智能体集合（@ 选择，或群的默认对象）。其他成员只是"看得到"                                                                                                 |
| 群上下文           | (智能体, 群) 的 Codex thread：这个智能体在这个群里聊过什么。按群隔离                                                                                                       |
| 长期记忆           | 智能体跨群积累的事实（mem0）。按智能体隔离、跨群共享                                                                                                                       |
| 任务               | 执行单元：看板上的 #N，指派给你自己或远程电脑上的编码智能体。可以有"来源群"                                                                                                |
| 讨论成员 vs 执行者 | 群成员是 AXP 智能体，负责讨论、起草、审阅；任务执行者是任务的指派对象（你或远程智能体），由任务系统的 Run 驱动。两者不混                                                   |

## 4. 产品流程

1. **新建群**：侧栏"＋ 新建群" → 名字（必填，可让智能体稍后改）+ 选成员（至少一个智能体）+ 可选目标。只选一个智能体也成立；之后可在成员栏邀请/移除。
2. **邀请/移除**：邀请后它第一次被点名时，群头会说明它是新成员，skill 让它先用 `group_info` 和 `read_group` 看简报和最近的消息；移除只是不再唤醒它，它的发言保留，它在该群的 Codex thread 归档。
3. **说话**：单智能体群和私聊里，每条消息都发给那个智能体。多智能体群里用 `@` 点名，可以点多个，`@所有人` 显式选全部；**没有 @ 的消息只作为上下文发出，不唤醒任何人**，被点名的智能体之后会按 skill 读到它。输入框下的状态行写明这条会唤醒谁，或「只作为上下文」。
4. **讨论形成任务**：任何时候点"起草任务"或对智能体说"把这个整理成任务"——智能体用群聊插件的 `draft_task` 在群里产出一张**任务草稿卡**（标题、目标、决定、验收、建议指派），你在卡上改字、选指派后点"创建"。也可以直接拆成多张草稿。草稿不进看板，创建后才有 #N。群也可以一个任务都没有。
5. **跟进执行**：群的侧栏有简报（目标、已定）和相关任务。任务卡片随状态实时更新（排队/运行/待验收/完成、PR、Artifact），点开看完整时间线和执行记录，不离开群。
6. **对执行说话**：在群里对任务卡点"回复给执行者"（或 `#12` 前缀），这条话作为任务评论发出（远程智能体照常排一次 Run）；群里只显示"已转给 #12"。反过来，远程智能体的评论不逐条刷进群，只在卡片上显示最新一条和计数。
7. **归档**：群没有状态。做完的群可以归档，从列表收起，不删任何东西，找回后可以继续聊。

减少复制切换的关键是三点：草稿卡（不用把讨论复制进任务描述）、群内任务卡（不用切到任务页看进度）、"回复给执行者"（不用切到任务页写评论）。

## 5. 群与任务的关系：方案对比

| 维度             | A. 群即任务（1:1）                                                 | B. 群关联多个任务（1:N，群只是讨论区） | **C. 推荐：群是主题，任务是派出的执行单元（1:N，默认 1）**                         |
| ---------------- | ------------------------------------------------------------------ | -------------------------------------- | ---------------------------------------------------------------------------------- |
| 用户感受         | 最贴近"群就是这件事"：群有状态、有指派                             | 群和任务是两样东西，要自己对应         | 群就是"这件事"（有目标、状态、简报）；只有一个任务时界面把它合在群头部，几乎就是 A |
| 拆分多个执行     | 难：要么开子群，要么一个任务多个执行者（现有 Run 模型不支持）      | 自然                                   | 自然：群里多张任务卡                                                               |
| 独立创建任务     | 每个任务都有群：看板上新建任务 = 新建群                            | 任务可以没有群                         | 任务可以没有群；需要讨论时在属性的「群」一行点「新建群讨论」                       |
| 任务时间线 vs 群 | 要合并 `task_activity` 与群消息，或者二选一当真相——改动最大        | 各自独立，靠链接                       | 任务时间线仍是执行的真相；群里只有一张随时间线变化的卡片，不复制                   |
| 远程 Run 触发    | "每条评论排一次 Run"遇到群聊就成了"每条群消息都派活"，必须另加区分 | 不变                                   | 不变；只有"回复给执行者"才成为评论                                                 |
| 旧任务迁移       | 每个旧任务都要生成群                                               | 不需要                                 | 不需要；旧任务打开时没有群，按需建                                                 |
| Project（#103）  | 群 = 任务，Project 挂在任务上                                      | Project 挂两处                         | Project 挂在群上，派出的任务默认继承；独立任务自己挂                               |
| Telegram（#102） | 一个 Telegram 群对应一个任务，太细                                 | Telegram 群对应 AXP 群                 | 同 B：Telegram 群（或话题）绑定 AXP 群，消息同样走"发言对象"规则                   |
| 实现量           | 大                                                                 | 小                                     | 中：群 + 任务 `source_thread` + 卡片投影                                           |

推荐 C，理由：它不把讨论消息和执行时间线搅在一起，不改现有 Run 语义，也给拆分留了路。

**已确认：松绑定。** 群可以没有任务。任务和群的关联是可选的、多对一：在群里起草创建的任务自动关联到这个群；在看板或别处创建的任务，可以在任务详情里「关联到群」，也可以取消。群的侧栏（宽屏是工作区面板的「群」tab，手机是群信息页）列出相关任务。不做「只有一个任务时群就是任务」的合并界面。

**群的状态**：不要。早先设想过的「讨论中 / 执行中 / 已完成」只用来给列表排序和收起做完的群；群和任务松绑定之后它没有意义，已确认去掉，只保留「归档」。

## 6. 多智能体回应策略

**唤醒规则**（控制面决定，智能体不轮询）：

1. 你的消息唤醒"发言对象"里的每个智能体，每个一条命令、一个回复占位。单智能体群就是它。
2. 多智能体群里没 @ 的消息**不唤醒任何人**，只作为上下文留在群里。不做「让模型判断谁该回」的隐式路由——可预测比聪明重要。
3. **智能体的发言默认不唤醒任何人**，即使正文里写了 @。看到 ≠ 被叫到 ≠ 要执行。智能体要找另一个智能体，只能调用 `mention` 工具（见下）。
4. **智能体找智能体：`mention` 工具**（首版就有）。
   - `mention(agent, message)` 唤醒另一个智能体，把话交给它。正文里随手写的 @ 不算。
   - **只通知，不回叫**：B 回复后不会自动唤醒 A。A 想看 B 的回答，要等它下次被唤醒时用 `read_group` 读。
   - **在发生的地方显示**：这次往来留在 A 调用 `mention` 的那个上下文里。你在和 A 私聊时让它「去找一下 B」，B 被唤醒在这段私聊里、回复也显示在这里（标成「Aria → Bolt」）；在某个群里发生的就显示在那个群里。不另开智能体之间的私聊。B 会为这个上下文得到一条自己的 Codex thread，读写这里的历史，和成员一样。
   - **被叫的智能体不在群里也可以**（你管不了智能体想找谁）。这时它只是这一次的参与者，不是成员；群里会提示一行「Bolt 和这里的讨论有关，可以拉进群」，带「邀请」按钮。私聊里同样提示，按钮是「建一个群」。
   - **防循环**：从你的一条消息算起，智能体之间最多唤醒 **5 次**，不能叫自己。到上限就停下，在**那个上下文里**提示「Aria 和 Bolt 已经来回 5 次了，请你看一下」，等你的下一条消息再重新计数。「全部停止」会连这一串一起停。
   - 这套规则复杂，出错的风险主要在模型怎么用工具。所以 `mention` 的工具说明和群聊 skill 要写清楚：什么时候该叫人、叫了以后别等回复、别为同一件事反复叫。
5. 唤醒时的输入很薄：被点名的那条消息，加一行群头（群名、成员、谁点名、自它上次说话以来有几条新消息）。**不做全量投递，也不注入摘要**；要不要看前情、看哪些，由群聊插件的 skill 规定，智能体用 `read_group` / `search_group` 自己取（§7.3）。

**并发与顺序**：

- @ 多个智能体：各自的容器并行跑；回复占位在发送时按 @ 顺序一次性写入，所以**显示顺序固定为点名顺序**，内容各自流式出现，不会因为谁先说完而跳动。
- 并行回答的智能体彼此看不到对方这一轮的回答（它们是兄弟），需要时用 `read_group` 读到。需要"B 看完 A 再说"时，用户分两条发，或第二阶段让 A 交接。
- 同一个智能体在另一个群里忙：命令排队（队列仍按智能体，一次一个），占位显示"在《X》里工作中 · 前面 n 条"。首版**不**在一个容器里并行跑两个群（共享工作区和 CPU，见 §7.2）；这一点已确认接受。

**停止与插话**：每个回复有自己的停止；群头部有"全部停止"（停这个群里所有进行中的回复，不影响这些智能体在别的群的工作）。插话只进入**同一群里**该智能体正在运行的 turn；它正在别的群里跑时，插话退化为排队，并在发送时说明。

**状态**：成员头像旁显示 空闲 / 在本群工作 / 在别的群工作 / 等待确认 / 不可用。审批照旧出现在那条回复上，"待处理"里标出群名。一个智能体失败只让它的回复失败，同一条消息的其他回复不受影响；"重试"只重试这一个。

**讨论成员 vs 执行者**：群成员（AXP 智能体）不会因为群里的讨论被派去"执行任务"；执行只发生在任务被创建并指派之后，由任务 runner 驱动远程智能体。群成员可以被请来"审阅 #12"，那是一次普通的被点名回答，不是任务 Run。

## 7. Runtime、上下文与事件

### 7.1 (智能体, 群) → Codex thread

- 控制面记一张映射：(智能体, 群) → Codex thread id、状态（new / ready / archived / failed）、该智能体在此群已见到的消息 seq。取代 `agent_session` 的"一智能体一行"。
- 命令带上群；`POST /prompt`、`/steer`、`/compact` 带 `thread_key`（群 id）和已知的 Codex thread id（首次为空）。
- runtime 的 `Agent` 从"一个 threadId"改为"按群懒加载的 thread 表"：首次见到某群时 `thread/start`（cwd 见 7.2）并发出 `thread.opened {thread_key, codex_thread_id}`；控制面记下。之后 `thread/resume` 指定的 id。**不再用 `thread/list` 猜**。resume 失败照旧报 `RECOVERY_RESUME_FAILED`，只影响该群，不另起 thread。
- 首版仍然"一个 runtime 同一时刻一个 turn"（`owner` 单值不变），只是 turn 属于不同 thread；这让审批、停止、boot_id 的现有保证原样成立。
- 压缩按群进行（`thread/compact/start` 带该群的 thread id）。
- 迁移：应用里不写迁移代码，现有数据由实施者上线时手工迁一次，见 [#237](https://github.com/AkaraChen/axp/issues/237)。

### 7.2 工作区

**已确认：不按群分工作目录。** 每个智能体只有自己的一个工作区（`/agent/workspace`，所有群的 thread 都以它为 cwd），就像每个人有自己的一份 clone。两个智能体需要对齐状态时，像人一样互相说（见 §6 的交接），而不是共享目录。

### 7.3 内置环境包：群聊与记忆（不可关闭）

群的行为和记忆都以内置环境包的形式装进每个智能体：智能体通过插件的 MCP 工具和 skill 使用它们，不走 `axp` 之类的 CLI，也不在工作区里写 `MEMORY.md`。

**必选的环境包**。现在新建智能体时默认载入全部内置环境包，但每个都可以取消。新增一个概念：`bundle.json` 里写 `"required": true`。

- 智能体编辑器里，这样的环境包显示为勾选并锁定（「内置，不可关闭」）。
- `POST/PATCH /api/v1/agents` 自动补上，去不掉。
- 现有智能体补上 `memory` 和 `groups` 是上线时的一次性手工迁移（#237），不写进应用。
- 它们不声明需要用户填写的配置，所以不会因为配置不全被禁用。

**「当前群」由平台给出，不由智能体自报。** 同一个智能体同一时刻只跑一个 turn（§6），控制面知道这个 turn 属于哪个群。runtime 网关的 forward auth 在注入 `X-AXP-Agent-Id` 的同时注入 `X-AXP-Group-Id`。插件的工具只能读写这个智能体所在的群，从结构上不会串话；记忆插件用同一个头记下来源群。

**群聊环境包（`groups`）**：一个插件，带 MCP 服务器（streamable HTTP，`${AXP_GATEWAY_URL}/groups/mcp`，Bearer agent key；网关核对后转给控制面内部 API，和 tasks 插件同一条路）和 skill。

| 工具                                 | 作用                                                                                | 阶段 |
| ------------------------------------ | ----------------------------------------------------------------------------------- | ---- |
| `read_group(after?, before?, limit)` | 按 seq 翻本群消息（默认读它上次说话之后的），包括其他智能体的回复、系统事件、任务卡 | P1   |
| `search_group(query, limit)`         | 在本群历史里检索相关的消息（先用 PostgreSQL 全文检索，之后可以加向量）              | P1   |
| `group_info()`                       | 群名、成员与忙闲、简报、关联任务                                                    | P1   |
| `update_brief(goal?, decided?)`      | 更新群简报（目标、已定），群里记一条系统事件                                        | P2   |
| `draft_task(...)`                    | 在群里产出任务草稿卡（ref `task_draft`），用户在卡上确认后才创建                    | P2   |
| `mention(agent, message)`            | 唤醒另一个智能体（可以不是成员），往来显示在当前上下文，只通知不回叫，5 次上限      | P1   |

skill（`groups/SKILL.md`）规定行为，大意是：

- 你在群里，只回应点名你的那条消息；没点名你的消息只当背景，不去执行。
- 回答前先判断需不需要前情。需要时先 `read_group` 看你上次说话以来的新消息，再按关键词 `search_group` 找相关的决定、数据和链接；只取够用的，不要整段翻历史。
- 别重复别人已经汇报过的内容。只有做事的人汇报进展。
- 讨论出可执行的事时用 `draft_task` 起草，由用户确认后创建；除非用户明确要求，不直接 `create_task`。
- 定下来的事用 `update_brief` 记进简报。
- 你知道的别的群的事来自记忆；引用时说明来自哪个群。

**记忆环境包（`memory`）**：现有的 memory 插件和 memory-service 不变（每轮召回、每轮抽取、`remember`/`recall`/`forget`），只是改为必选。

- **跨群共享，按智能体隔离**（mem0 `user_id = agent`），没有「本群不写入」之类的开关。A 群定下的事在 B 群通过召回自然知道。这是跨群知识的唯一通道，不另做跨群检索。
- 抽取时把 `X-AXP-Group-Id` 记进记忆的 metadata，召回时每条前标出来源群名，记忆页可以按群筛选。这是标注，不是隔离。`stop` hook 在 turn 结束前运行，这时命令仍在执行，能拿到当前群；万一拿不到，记成无来源。
- hook 的暂存按 `turn_id` 区分（`plugins/memory/hooks/memory.mjs`），已核实多 thread 不会冲突。

### 7.4 从讨论到执行的快照

- `draft_task`（群聊插件的工具）产出草稿卡：标题、目标、决定、验收、来源消息范围；草稿存在群里（一条特殊消息），可编辑，不进看板。
- 创建时把草稿**定稿为任务描述**（这一刻的快照，之后群里的讨论不会悄悄改任务），任务记 `source_thread` 和来源消息范围，描述末尾带"来源：群《X》"链接。远程智能体只读任务描述，不需要读群。
- 之后要追加：卡片上的"回复给执行者"→ 任务评论（触发 Run）；"更新任务描述"→ 让智能体重新起草差异，你确认后改描述（时间线记一条修改）。

### 7.5 结果回群，不重复

- 真相在 `task_activity`。群里每个任务**一张卡片**（一条特殊消息，按 revision 更新，而不是每个事件一条新消息），显示状态、执行者、最新一条远程评论、PR、Artifact、"待你验收"按钮。
- 远程智能体的 `axp artifact upload` 照旧挂任务；群卡片从任务读到它。AXP 智能体在群里 `publish_artifact` 时卡片出现在那条回复里（现有机制）。
- 想让群里的智能体审阅结果：在卡片上"请 @A 审阅"——一次普通唤醒，输入里带任务 id，它用 `get_task` 读，`comment_task` 回。

### 7.6 事件与重连

- 仍是一条工作区 SSE 流（`ui_event`），游标语义不变；`message.updated`、`interaction.updated` 的载荷加群 id；新增 `thread.updated`（名字、成员、简报、状态、未读）、`task_card.updated` 可以并入 `message.updated`（卡片就是消息）。
- 重连按游标补齐，浏览器按 revision 去重——与现在一样。快照接口改为"群列表 + 活跃回复 + 待处理"，群历史按群分页。
- 幂等：消息 id 兼作 `Idempotency-Key` 不变；一条消息唤醒多个智能体是**一个事务**里写入用户消息 + n 个回复占位 + n 条命令，重试不会多派。
- 未读：每个群记"你读到的 seq"，侧栏显示未读数。

### 7.7 兼容

- 应用没有发布，不保留旧接口：按智能体分页的历史、按智能体存的草稿，在 Web 切换到群之后直接删掉。
- tasks 插件现有工具（`create_task`、`get_task`、`comment_task`、`update_task`、`list_*`）不变；群相关的工具都在群聊插件里（§7.3）。在群里的 turn 中调用 `create_task` 时，控制面按 `X-AXP-Group-Id` 自动记下来源群。
- 任务详情的讨论入口只放在属性的「群」一行：已关联群时「在群里讨论」打开它；未关联时「新建群讨论」复用建群流程，以任务为目标、邀请所选智能体并关联任务。底部保留 #238 的「请 Agent 协助」及其对话框，用于远程执行侧的协助。
- `axp` CLI 与远程智能体不受影响。

## 10. 决定记录

都已确认（2026-10-13）：

1. 群和任务**松绑定**：群可以没有任务；任务可以关联一个群；群的侧栏列出相关任务。
2. 群**没有状态**，只能归档。
3. 多智能体群里**没 @ 的消息只作为上下文**，不唤醒任何人；单智能体群和私聊里的每条消息都发给那个智能体。
4. **不按群分工作目录**，每个智能体一个工作区。
5. 智能体之间用 **`mention` 工具**：往来显示在发生的上下文里；只通知，不回叫；从你的一条消息算起最多 5 次，到上限在那里提醒你审阅；可以叫群外的智能体，群里提示可以把它拉进来；过程可见，可以全部停止。
6. 长期记忆**跨群共享**，走现有的记忆插件；记忆和群聊都是内置、不可关闭的环境包；不写 `MEMORY.md`。
7. **私聊**每个智能体只有一个，存储和抽象上都是群；想和同一个智能体开多段，就建多个只拉它的群。现有数据**不在应用里迁移**，见 #237。
8. 接受同一个智能体跨群串行、在别的群忙时排队。
9. 宽屏对话页加上侧栏；手机用 **A 列表优先 + 底部标签**。
