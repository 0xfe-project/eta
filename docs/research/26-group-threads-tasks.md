# 26 群（Thread）与「讨论 → 任务」的统一协作流程（设计稿）

AXP 任务 #111。这是一份**待讨论的设计**，不是已定方案：本 PR 只有这份文档和一个可交互的原型（`docs/research/26-group-threads/prototype/`），不改业务代码。第 10 节是需要你拍板的问题。

## 0. 摘要

- **今天的事实**：一个智能体 = 一段对话 = 一个 Codex thread。三者在数据库（`message.agent_id`、`agent_session` 一行）、runtime（`Agent` 只有一个 `threadId`）和前端（草稿、附件、outbox 都按智能体）里是绑死的。要有多个群，必须先把「智能体」和「对话上下文」拆开。
- **推荐**：新增一等对象 **群**（内部叫 thread）。群有名字、成员（你 + 1..n 个 AXP 智能体）、目标/简报和状态；它本身就代表「这件事」。**任务仍是执行单元**，从群里一键派出，默认一个群对应一个任务，需要时拆成多个；任务的执行（远程 Run、评论、交付物）仍由任务系统管理，群里只显示一张实时更新的卡片，不复制时间线。
- **上下文隔离**：每个「(智能体, 群)」一条独立的 Codex thread；同一智能体的长期记忆跨群共享（它是"这个智能体知道什么"），群的对话上下文不共享（它是"这件事聊到哪了"）。
- **多智能体**：只有被点名（或群的默认对象）才被唤醒；智能体的发言默认**不唤醒**别的智能体；看到 ≠ 要执行。首版就支持在一个群里 @ 多个智能体并行回答，交接（智能体 @ 智能体）放第二阶段并带跳数预算。
- **首版范围**：命名群（最少你 + 1 个智能体）、群列表、成员增删、@ 选择发言对象、多智能体并行回答、从群起草并创建任务、任务卡片回群、旧对话迁移为每个智能体一个"私聊群"。不做多用户/权限/SaaS，不碰 #102 Telegram、#103 Project 的实现。

## 1. 现状审计

代码路径相对 `apps/control-plane/internal`（Go）、`apps/agent-runtime/src`（runtime）、`apps/web/src`（Web）。

| 方面         | 现在是什么                                                                                                                                                             | 对多群的含义                                                                                                    |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 对话容器     | `conversation` 表只有一行 `is_default`（`chat.DefaultConversationID`），它其实是**整个工作区**：`agent.conversation_id`、`ui_event`、`agent_event` 的 seq 都挂在它上面 | 不要把它改成"群"——它是事件流的分区。群是新对象，`conversation` 保持"工作区"的含义                               |

| 幂等         | 客户端生成消息 id，兼作 `Idempotency-Key`（`api_idempotency`）；outbox 在 localStorage `axp.chat.v1`，**按智能体**顺序发送                                             | 机制不变，outbox/草稿的键从智能体改为群                                                                         |
| 审批         | `approval` 挂在 `command_id`，`interaction` 挂在 `message_id` 和 conversation；"待处理"跨智能体汇总                                                                    | 通过命令/消息自然带上群；待处理列表要显示"哪个群"                                                               |
| 插话 / 停止  | steer 进入**该智能体正在运行的 turn**；stop 按回复                                                                                                                     | 插话必须限定"同一群的运行中 turn"，否则会把 A 群的话插进 B 群                                                   |
| 附件         | `chat_attachment.agent_id`，上传到"当前智能体"；runtime 网关只放行本智能体的附件                                                                                       | 一条消息可能发给多个智能体：附件改为属于群，网关校验"智能体是该群成员"                                          |
| Artifact     | `artifact(agent_id 或 computer_id, task_id)`；工具结果 `_meta["axp/ref"]` 投影成活动卡片                                                                               | 卡片天然出现在发布它的那条回复里，即那个群；可选再记 `thread_id` 让群侧栏能列出                                 |
| 任务         | `task / task_session / task_run / task_activity`；指派远程智能体后每条评论排一次 Run；AXP 智能体**不是指派对象**；`created_by_agent`                                   | 任务模型不用大改；缺的是"来源群"和"群内卡片"                                                                    |
| 任务 ↔ 聊天  | 任务详情的「让智能体反馈」（`components/workspace/tasks.tsx`）把一段固定文字作为聊天消息**塞进该智能体唯一的对话**，智能体再用 `get_task`/`comment_task`               | 这正是现在"串话 + 来回切换"的来源：任务讨论污染私聊上下文，结果又只在任务里。群出现后它变成"在该任务的群里讨论" |
| 记忆         | mem0 `user_id = agent`（`X-AXP-Agent-Id`），每轮 `prompt_submit` 召回、`stop` 抽取；**没有群/对话维度**                                                                | 默认按智能体共享是对的；但 A 群的事实会被 B 群召回。需要来源标注和"本群不记忆"的开关（见 §7.3）                 |
| 工作区文件   | 卷 `/agent/workspace` 是 Codex 的 cwd，按智能体一份                                                                                                                    | 同一智能体在两个群里的工作会碰到同一批文件；首版串行执行可避免同时写，但目录约定要定（见 §7.2）                 |

结论：**串话的风险点有四个**——Codex 上下文（必须分 thread）、插话（必须限群）、附件（必须限成员）、记忆召回（默认共享但要可见、可关）。前三个是硬隔离，第四个是产品取舍。

## 2. Raft 参考：核实了什么、借鉴什么、不照搬什么

读了 `botiverse/raft-source` 的 manual 与 `packages/server/src/services`（FSL-1.1，只参考设计，不复制实现）。

- **模型**：channel / DM 存消息；thread 是挂在某条消息下的子讨论，不能独立创建；task 是"顶层消息 + 任务元数据"（编号、状态、认领人），thread 回复不能变成任务（`manual/agent-knowledge/thread.md`、`task.md`）。
- **投递与唤醒**：频道成员**按成员关系**收到每条消息进自己的 inbox（`mention.md`："membership delivers regardless of mention"）；thread 按"关注者"投递；@ 只是"注意力"信号。Agent 是**一个常驻 session 横跨所有频道**，被唤醒后用 `raft message check` 抽干 inbox 再决定回不回（`inbox.md`），唤醒有计划器和崩溃熔断（`agentOrchestrator.wakePlan`、`wakeCrashLoopBreaker`）。
- **借鉴**：人和智能体都是参与者；"可见"和"被投递/被唤醒"是两件事；任务有认领、状态、编号；有防崩溃循环的熔断。
- **不照搬**：
  1. Raft 的 thread 是附属物，你要的是**独立命名的主题群**，所以 AXP 的"群"对应 Raft 的 channel，而不是 thread。
  2. Raft 让每个成员 agent 收到所有消息并自行判断——成本高，且一个 session 混着所有频道的上下文。AXP 的智能体是 Codex app-server 驱动的容器，每次唤醒就是一个付费 turn，所以 **AXP 由控制面决定唤醒谁**，智能体不自己轮询 inbox。
  3. Raft 任务 = 消息；AXP 已有独立的任务看板、远程 Run 和时间线，任务不应退化成一条消息。

## 3. 概念

| 概念               | 含义                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 群（thread）       | 一个命名的工作主题。成员 = 你 + 1..n 个 AXP 智能体。有目标/简报、状态、归档                                              |
| 私聊群             | 只有你和一个智能体、没有特意命名的群；现有每个智能体的对话迁移成它                                                       |
| 发言对象           | 一条消息要唤醒的智能体集合（@ 选择，或群的默认对象）。其他成员只是"看得到"                                               |
| 群上下文           | (智能体, 群) 的 Codex thread：这个智能体在这个群里聊过什么。按群隔离                                                     |
| 长期记忆           | 智能体跨群积累的事实（mem0）。按智能体隔离、跨群共享                                                                     |
| 任务               | 执行单元：看板上的 #N，指派给你自己或远程电脑上的编码智能体。可以有"来源群"                                              |
| 讨论成员 vs 执行者 | 群成员是 AXP 智能体，负责讨论、起草、审阅；任务执行者是任务的指派对象（你或远程智能体），由任务系统的 Run 驱动。两者不混 |

## 4. 产品流程

1. **新建群**：侧栏"＋ 新建群" → 名字（必填，可让智能体稍后改）+ 选成员（至少一个智能体）+ 可选目标。只选一个智能体也成立；之后可在成员栏邀请/移除。
2. **邀请/移除**：邀请时可选"让它读一下前情"（把简报和最近 N 条消息作为它第一次被唤醒时的上下文）；移除只是不再唤醒它，它的发言保留，它在该群的 Codex thread 归档。
3. **说话**：输入框左侧是"发给"chip：单智能体群固定是它；多智能体群默认是**上一次的对象**（不是所有人），`@` 改对象，可多选，`@所有人`显式选全部。消息里的 @ 与 chip 同步。
4. **讨论形成任务**：任何时候点"起草任务"或对智能体说"把这个整理成任务"——智能体用 tasks 工具 `draft_task`（新）在群里产出一张**任务草稿卡**（标题、目标、决定、验收、建议指派），你在卡上改字、选指派后点"创建"。也可以直接拆成多张草稿。草稿不进看板，创建后才有 #N。
5. **跟进执行**：群顶部固定"简报"（目标/决定/关联任务）。任务卡片随状态实时更新（排队/运行/待验收/完成、PR、Artifact），点开在右侧栏看完整时间线和执行记录，不离开群。
6. **对执行说话**：在群里对任务卡点"回复给执行者"（或 `#12` 前缀），这条话作为任务评论发出（远程智能体照常排一次 Run）；群里只显示"已转给 #12"。反过来，远程智能体的评论不逐条刷进群，只在卡片上显示最新一条和计数。
7. **完成/归档**：任务全部完成时群顶部提示"标记完成？"；完成的群从活跃列表下沉，**仍可继续聊**（继续说话自动回到"讨论中"）。归档只是隐藏，不删任何东西。

减少复制切换的关键是三点：草稿卡（不用把讨论复制进任务描述）、群内任务卡（不用切到任务页看进度）、"回复给执行者"（不用切到任务页写评论）。

## 5. 群与任务的关系：方案对比

| 维度             | A. 群即任务（1:1）                                                 | B. 群关联多个任务（1:N，群只是讨论区） | **C. 推荐：群是主题，任务是派出的执行单元（1:N，默认 1）**                         |
| ---------------- | ------------------------------------------------------------------ | -------------------------------------- | ---------------------------------------------------------------------------------- |
| 用户感受         | 最贴近"群就是这件事"：群有状态、有指派                             | 群和任务是两样东西，要自己对应         | 群就是"这件事"（有目标、状态、简报）；只有一个任务时界面把它合在群头部，几乎就是 A |
| 拆分多个执行     | 难：要么开子群，要么一个任务多个执行者（现有 Run 模型不支持）      | 自然                                   | 自然：群里多张任务卡                                                               |
| 独立创建任务     | 每个任务都有群：看板上新建任务 = 新建群                            | 任务可以没有群                         | 任务可以没有群；需要讨论时"在群里讨论"懒创建一个                                   |
| 任务时间线 vs 群 | 要合并 `task_activity` 与群消息，或者二选一当真相——改动最大        | 各自独立，靠链接                       | 任务时间线仍是执行的真相；群里只有一张随时间线变化的卡片，不复制                   |
| 远程 Run 触发    | "每条评论排一次 Run"遇到群聊就成了"每条群消息都派活"，必须另加区分 | 不变                                   | 不变；只有"回复给执行者"才成为评论                                                 |
| 旧任务迁移       | 每个旧任务都要生成群                                               | 不需要                                 | 不需要；旧任务打开时没有群，按需建                                                 |
| Project（#103）  | 群 = 任务，Project 挂在任务上                                      | Project 挂两处                         | Project 挂在群上，派出的任务默认继承；独立任务自己挂                               |
| Telegram（#102） | 一个 Telegram 群对应一个任务，太细                                 | Telegram 群对应 AXP 群                 | 同 B：Telegram 群（或话题）绑定 AXP 群，消息同样走"发言对象"规则                   |
| 实现量           | 大                                                                 | 小                                     | 中：群 + 任务 `source_thread` + 卡片投影                                           |

推荐 C，理由：它保留了"群代表这件事"的感受（群有自己的目标和状态，单任务时 UI 合一），同时不把讨论消息和执行时间线搅在一起，不改现有 Run 语义，也给拆分留了路。

**群的状态**：推荐由用户手动设置的简单状态（讨论中 / 执行中 / 已完成），"执行中"在派出第一个任务时自动设置、"任务都完成"时**提示**而不自动改；不复用任务的 7 种状态，避免两套状态互相同步。这是待定项 Q1。

另一个可以讨论的变体：**A′——每个任务都有群，但群不一定有任务**（群 ⊇ 任务讨论）。它让"任务详情 = 群"成立，代价是旧任务迁移和看板新建都要建群。首版可以先做 C，再按使用情况决定是否走到 A′。

## 6. 多智能体回应策略

**唤醒规则**（控制面决定，智能体不轮询）：

1. 你的消息唤醒"发言对象"里的每个智能体，每个一条命令、一个回复占位。单智能体群就是它。
2. 多智能体群没 @ 时，对象是该群"上一次的对象"（chip 上可见，可改）；新群第一次没 @ 时是创建时排第一的智能体。不做"让模型判断谁该回"的隐式路由——可预测比聪明重要。
3. **智能体的发言默认不唤醒任何人**，即使正文里写了 @。看到 ≠ 被叫到 ≠ 要执行。
4. 第二阶段：智能体可用工具 `hand_off(agent, note)` 显式把话交给另一个成员，界面显示"A → B"。防循环：同一条你的消息引发的交接链**最多 3 跳**、每个智能体在同一链上最多被唤醒 1 次、不能交给自己；超出时停下并在群里提示"需要你决定"。用户的下一条消息重置预算。
5. 没被唤醒的成员下一次被唤醒时，控制面把它**没见过的群消息**（你和其他智能体的）作为一段"群里的新消息（未点名你，仅供参考）"放在本轮输入前面，按 seq 计；太长时只放摘要行和条数，它可以用 `read_thread` 工具翻原文。

**并发与顺序**：

- @ 多个智能体：各自的容器并行跑；回复占位在发送时按 @ 顺序一次性写入，所以**显示顺序固定为点名顺序**，内容各自流式出现，不会因为谁先说完而跳动。
- 并行回答的智能体彼此看不到对方这一轮的回答（它们是兄弟），下一轮通过第 5 条看到。需要"B 看完 A 再说"时，用户分两条发，或第二阶段让 A 交接。
- 同一个智能体在另一个群里忙：命令排队（队列仍按智能体，一次一个），占位显示"在《X》里工作中 · 前面 n 条"。首版**不**在一个容器里并行跑两个群（共享工作区和 CPU，见 §7.2）。

**停止与插话**：每个回复有自己的停止；群头部有"全部停止"（停这个群里所有进行中的回复，不影响这些智能体在别的群的工作）。插话只进入**同一群里**该智能体正在运行的 turn；它正在别的群里跑时，插话退化为排队，并在发送时说明。

**状态**：成员头像旁显示 空闲 / 在本群工作 / 在别的群工作 / 等待确认 / 不可用。审批照旧出现在那条回复上，"待处理"里标出群名。一个智能体失败只让它的回复失败，同一条消息的其他回复不受影响；"重试"只重试这一个。

**讨论成员 vs 执行者**：群成员（AXP 智能体）不会因为群里的讨论被派去"执行任务"；执行只发生在任务被创建并指派之后，由任务 runner 驱动远程智能体。群成员可以被请来"审阅 #12"，那是一次普通的被点名回答，不是任务 Run。

## 7. Runtime、上下文与事件

### 7.1 (智能体, 群) → Codex thread

- 控制面记一张映射：(智能体, 群) → Codex thread id、状态（new / ready / archived / failed）、该智能体在此群已见到的消息 seq。取代 `agent_session` 的"一智能体一行"。
- 命令带上群；`POST /prompt`、`/steer`、`/compact` 带 `thread_key`（群 id）和已知的 Codex thread id（首次为空）。
- runtime 的 `Agent` 从"一个 threadId"改为"按群懒加载的 thread 表"：首次见到某群时 `thread/start`（cwd 见 7.2）并发出 `thread.opened {thread_key, codex_thread_id}`；控制面记下。之后 `thread/resume` 指定的 id。**不再用 `thread/list` 猜**。resume 失败照旧报 `RECOVERY_RESUME_FAILED`，只影响该群，不另起 thread。
- 首版仍然"一个 runtime 同一时刻一个 turn"（`owner` 单值不变），只是 turn 属于不同 thread；这让审批、停止、boot_id 的现有保证原样成立。
- 压缩按群进行（`thread/compact/start` 带该群的 thread id）。
- 迁移：现有智能体的那条 thread 就是它"私聊群"的 thread——控制面在迁移时用 runtime 报告的 `runtime.started.thread_id` 填映射，旧历史一条不丢。

### 7.2 工作区

推荐每个群一个子目录作为该 thread 的 cwd：`/agent/workspace/threads/<群 id>`，私聊群沿用 `/agent/workspace` 根（兼容现有历史里的相对路径）。这样两个群的产物不会互相覆盖，智能体仍可以 `cd ..` 访问共享内容。待定项 Q4。

### 7.3 长期记忆与群上下文

- **群上下文**：只在该群的 Codex thread 里。A 群聊过的内容在 B 群里不会出现在对话历史中。
- **长期记忆**：按智能体（mem0 `user_id = agent`）跨群共享——这是"它知道你喜欢什么、项目约定是什么"。召回时可能带出别的群的事实，这是有意的，但：
  - 抽取时在记忆的 metadata 里记下来源群（已有 `source` 字段的同类扩展），记忆页能按群筛选；
  - 群设置里有"本群不写入长期记忆"（hook 读到该标记就跳过 `capture`，召回不受影响）；
  - 召回时把来源群名写在每条记忆前，让模型知道这是"别处"的事实。

### 7.4 从讨论到执行的快照

- `draft_task`（tasks 插件新工具）产出草稿卡：标题、目标、决定、验收、来源消息范围；草稿存在群里（一条特殊消息），可编辑，不进看板。
- 创建时把草稿**定稿为任务描述**（这一刻的快照，之后群里的讨论不会悄悄改任务），任务记 `source_thread` 和来源消息范围，描述末尾带"来源：群《X》"链接。远程智能体只读任务描述，不需要读群。
- 之后要追加：卡片上的"回复给执行者"→ 任务评论（触发 Run）；"更新任务描述"→ 让智能体重新起草差异，你确认后改描述（时间线记一条修改）。

### 7.5 结果回群，不重复

- 真相在 `task_activity`。群里每个任务**一张卡片**（一条特殊消息，按 revision 更新，而不是每个事件一条新消息），显示状态、执行者、最新一条远程评论、PR、Artifact、"待你验收"按钮。
- 远程智能体的 `axp artifact upload` 照旧挂任务；群卡片从任务读到它。AXP 智能体在群里 `publish_artifact` 时卡片出现在那条回复里（现有机制）。
- 想让群里的智能体审阅结果：在卡片上"请 @A 审阅"——一次普通唤醒，输入里带任务 id，它用 `get_task` 读，`comment_task` 回。

### 7.6 事件与重连

- 仍是一条工作区 SSE 流（`ui_event`），游标语义不变；`message.updated`、`interaction.updated` 的载荷加群 id；新增 `thread.updated`（名字、成员、简报、状态、未读）、`task_card.updated` 可以并入 `message.updated`（卡片就是消息）。
- 重连按游标补齐，浏览器按 revision 去重——与现在一样。快照接口改为"群列表 + 活跃回复 + 待处理"，群历史按群分页。
- 幂等：消息 id 兼作 `Idempotency-Key` 不变；一条消息唤醒多个智能体是**一个事务**里写入用户消息 + n 个回复占位 + n 条命令，重试不会多派。
- 未读：每个群记"你读到的 seq"，侧栏显示未读数。

### 7.7 兼容

- `GET /agents/{id}/messages`、`POST /chat/messages {agent_id}` 继续可用，映射到该智能体的私聊群；Web 全部切换后再标为弃用。
- tasks 插件现有工具（`create_task`、`get_task`、`comment_task`、`update_task`、`list_*`）不变；新增 `draft_task`（以及第二阶段的 `hand_off`、`read_thread`），runtime 网关注入的身份之外再注入"当前群"，让 `create_task` 自动记来源群。
- 任务详情的「让智能体反馈」改为"在群里讨论"：有来源群就打开它，没有就以该任务为目标新建一个群并邀请所选智能体。
- `axp` CLI 与远程智能体不受影响。

## 10. 需要你决定的问题

1. **群与任务的关系**：C（推荐：群是主题，1:N 派任务，单任务时 UI 合一）、A（群严格等于一个任务）、还是 A′（每个任务都有群）？
2. **群的状态**：手动的"讨论中/执行中/已完成"（推荐），还是由任务状态推导，还是不要状态？
3. **默认发言对象**：多智能体群不 @ 时发给"上一次的对象"（推荐）、"群主持智能体"、还是"所有人"？
4. **工作目录**：每个群一个子目录（推荐），还是所有群共用 `/agent/workspace`？
5. **智能体之间的交接**：P3 再做并带 3 跳预算（推荐），还是首版就要？或者永远只由你点名？
6. **长期记忆**：跨群共享 + 来源标注 + 可按群关闭（推荐），还是默认按群隔离？
7. **私聊群**：迁移后每个智能体保留一个固定的私聊群（推荐），还是私聊也变成普通的、可以有多个的群？
8. **跨群并行**：同一智能体首版串行（推荐），能接受"它在别的群忙时要排队"吗？
