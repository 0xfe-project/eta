# 任务 #19：聊天交互与状态逻辑梳理与改进方案

> 调研基于 origin/main `3d9f567`。只读源码 + 组件级复现，未修改产品代码、未连生产、未起开发栈。
> 标注：**【已证实】** = 复现或代码路径可直接证明；**【推断】** = 代码支持但未在真实环境验证；**【待确认】** = 需要用户补充信息。

## 0. 一页结论

1. **重复发送的根因在前端发送链路**：发送期间没有任何"在途"状态——输入框不清空、不禁用，对话里也不出现这条消息；每次回车都是一次新请求，且每个请求的 `Idempotency-Key` 都是在 fetch 中间件里新随机生成的，服务端已有的幂等机制无法把"同一条消息的多次尝试"认出来。弱网下连按三次回车 = 三条独立消息。组件级复现已证实（见 §2 S1）。
2. **"两个正在恢复"**：代码里（含全部历史）没有"正在恢复"这一文案。最接近的现象已证实：每条排队中的回复都会各自渲染一条带动画、计时器和 "esc to interrupt" 的工作行（`排队中 (Ns • esc to interrupt)`），两条消息就是两条看起来都在"运行"的工作行；同时，容器冷启动/快照下载/会话恢复（最长 120 秒）这一阶段对用户完全不可见，也显示为"排队中"。我推断用户看到的就是这两者叠加，但**需要用户确认看到的确切文案/截图**。
3. **更深层的问题是"状态归属"混乱**：现在只有一种状态载体——"助手回复"消息的 `status`。它同时承担了"我的消息送达没有""在排第几""环境在启动/恢复""智能体在执行""失败了能不能重来"这五件事，而"送达"这一层根本不存在（在前端请求的 pending 里，不可见），"环境"这一层在内部存在但没有对外投影。
4. 建议的整体方向：**把状态分成三层、各归其主**——消息的"送达"（前端拥有）、回复的"执行"（服务端拥有、每条回复一个）、智能体的"环境"（服务端拥有、每个智能体一个），并且同一时刻每个智能体只有一个"活的"指示器。具体实现方式（客户端消息 ID、幂等键生命周期、排队托盘等）作为选项列出，等你选。

## 4. 根因分析

1. **没有"送达"这一层状态**（Q1 Q2 Q3 Q4 Q14）。消息只有在服务端创建后才存在；在此之前它只是一个看不见的请求。于是"我按了发送"与"消息存在"之间有一段对用户不可见的空窗，用户只能靠重复按键确认。
2. **幂等的作用域错了**（Q1 的技术面）。服务端 `idempotency.Do` 是好的，但前端在 _每个 HTTP 请求_ 上新建键，等于每次尝试都是新消息；它只能防网络栈层面的同请求重放，防不住"同一条消息的第二次尝试"。
3. **每条回复各自表达"在运行"**（Q5 Q7）。渲染规则是"活跃状态 → 渲染工作行"，没有"每个智能体只有一个执行中"的概念；排队与执行用的是同一个组件，只换了文字。
4. **智能体环境状态没有对外投影**（Q6 Q12）。`provisioning/recovering/ready` 只在内部；产品状态完全由"有没有活跃回复"推导，因此环境问题只能通过"每条消息"表达，要么不可见（等待），要么重复（失败 N 次）。
5. **意图结果不回传**（Q8 Q9 Q11）。插话被拒、执行中断、失败等结果只体现在回复状态上，没有"发生了什么 + 你可以做什么"。
6. **连接与草稿是"附带"的**（Q10 Q13）。它们没有被当作交互状态设计过。

不确定项：Q15 的确切现象；弱网重复是"请求挂起后集中到达"还是"响应丢失后用户重发"——两者都会发生，前者已复现；真实浏览器/HTTP2 对挂起 POST 的行为未在真实网络下测。

## 5. 交互原则（目标体验）

1. **按一次 = 一条消息。** 按下发送，消息立刻出现在对话里并清空输入框；之后的任何重试都是"这一条"的重试，不会变成第二条。
2. **每个状态只出现在它的主人身上。**
   - 送达（发送中 / 未送达）→ 属于 **user 消息**；
   - 执行（等待 / 执行中 / 等你确认 / 停止中 / 结束）→ 属于 **回复**；
   - 环境（启动中 / 恢复会话 / 不可用）→ 属于 **智能体**，只显示一次。
3. **每个智能体同一时刻只有一个"活的"指示器**：正在执行的那条。等待中的消息安静地标出位置，不动画、不计时、不提示 Esc。
4. **每个结束态都说清"执行了没有"并给出下一步**：未送达（没执行）→ 重试/编辑/丢弃；执行中断（不确定）→ 重新发送（明确是再发一次）；失败 → 重新发送；已停止 → 无。
5. **系统不确定时就说不确定**：连接断开、刷新后结果未知，都显式标出，并在恢复后自动校正。
6. **意图结果可见**：插话没插进去、排在第几、环境要多久，都给反馈。
7. **草稿属于我**：按智能体保存，刷新不丢，别的请求不会动它。

## 6. 目标状态模型

### 6.1 一条消息的生命周期（用户视角，三层合一）

```
             按发送
草稿 ───────────────▶ [发送中]  (前端；消息已在对话里，灰色/待确认标记)
                          │
          ┌───────────────┼──────────────────┐
     服务端确认          明确失败            超时/断网/刷新
          │          (4xx/5xx 可判定)        (结果未知)
          ▼               ▼                     ▼
      [已送达]        [未送达]  ◀── 校正：未找到 ── [确认中]
          │        重试 / 编辑 / 丢弃              │ 校正：找到了 → 已送达
          │        （重试 = 同一条）               
          ▼
  ┌── 回复 ─────────────────────────────────────────────────────────┐
  │ [等待中·第 n 条] ──轮到它──▶ [执行中] ⇄ [等你确认]                │
  │      │  撤回                      │ 停止            │             │
  │      ▼                           ▼                 ▼             │
  │  [已撤回]                    [停止中] ──▶ [已停止]                │
  │                    [执行中] ──▶ [完成] | [失败·可重新发送]         │
  │                               | [中断·结果不确定·可重新发送]       │
  └──────────────────────────────────────────────────────────────────┘

智能体（每个一份，独立于消息）：
  [空闲] ──有工作──▶ [启动环境] ──▶ [恢复会话] ──▶ [就绪/工作中] ──空闲10分钟──▶ [休眠]
                         └────────── 失败 ──────────▶ [不可用：原因 + 操作]
```

### 6.2 现状 → 目标映射

| 现在的回复 status               | 目标显示                                                    | 变化              |
| ------------------------------- | ----------------------------------------------------------- | ----------------- |
| （无，请求在途）                | user 消息"发送中"                                           | **新增层**        |
| （无，请求失败）                | user 消息"未送达 · 重试"                                    | **新增层**        |

## 8. 可选方案与取舍

**D1 怎样保证"按一次 = 一条"**

- **A. 消息有身份，重试复用它**（推荐方向）：在按下发送时就确定"这条消息"，后续自动/手动重试都携带同一身份；服务端用现有幂等机制即可识别。配合乐观显示。优点：弱网下可连续输入，能区分"未送达/确认中"。代价：前端多一个本地待送达列表，需要和服务端消息对齐（按身份去重）。
- **B. 在途期间锁定输入**：最简单，但弱网时输入框卡住、不能连续写，且解决不了"响应丢失后重发"。
- **C. 服务端按内容去重**：会误伤有意重复的消息，不推荐。

**D2 排队消息放在哪**

- **A. 留在对话里，只改表现**（等待中·第 n 条、静态、可撤回）：改动小，对话顺序 = 发送顺序。
- **B. 放到输入框上方的"待发送托盘"**，开始执行时才进入对话：对话顺序 = 执行顺序，可在执行前编辑/撤回；但和服务端"发送即创建消息"的模型不一致，改动大（涉及历史与插话的位置）。

**D3 环境状态要不要给用户看、看多细**

- **A. 公开一个智能体阶段**（启动环境 / 恢复会话 / 就绪 / 不可用），显示在智能体栏；
- **B. 不公开，只改文案**为"等待智能体就绪"。A 解决 Q6/Q12 更彻底，需要扩展公开 Agent 契约。

**D4 忙碌时回车的默认含义**：保持"排队"（现状）/ 改为"插话" / 输入框显式切换。无论哪种，插话退化为排队时都要提示。

**D5 失败后的"重新发送"语义**：生成一条新消息（历史里保留失败的那条）还是在原位置重跑。"执行中断，结果不确定"必须由用户明确确认，不能自动。

**D6 草稿**：按智能体保存 + 本地持久化；切换智能体时是否提示"有未发送草稿"。
